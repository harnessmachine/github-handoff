# GitHub Handoff

Сохраняй состояние одной рабочей задачи в GitHub Issue, чтобы новая сессия AI-агента могла продолжить работу без всей предыдущей переписки.

Главный сценарий должен работать по одной команде:

```text
Зафиксируй прогресс.
```

Не заставляй пользователя искать Issue, вставлять URL, пересказывать сессию или заполнять шаблон.

## Модель хранения

- описание Issue хранит задачу: цель, контекст, ограничения и критерии готовности;
- handoff-комментарий хранит состояние текущей сессии;
- код, документы, commits и Pull Request остаются в своих источниках и упоминаются ссылками или путями.

## Зафиксировать прогресс

Команда «зафиксируй прогресс», «сохрани сессию» или «сделай handoff» разрешает без дополнительного подтверждения:

- определить текущий GitHub-репозиторий;
- найти существующую Issue этой же задачи;
- создать одну новую Issue, если подходящей ещё нет;
- добавить один handoff-комментарий;
- вернуть готовый запрос для нового чата.

Сам извлеки факты из текущей сессии. Не проводи интервью и не проси пользователя заполнять поля.

### 1. Определи репозиторий

Используй первый однозначный источник:

1. репозиторий, явно названный в сессии;
2. репозиторий текущей рабочей папки из `git remote`;
3. единственный репозиторий, однозначно следующий из контекста.

Задай один короткий вопрос только если выбор между несколькими репозиториями реально изменит место записи.

### 2. Найди или создай Issue

Проверяй в таком порядке:

1. Issue, уже упомянутую или использованную в текущей сессии;
2. существующую открытую Issue с тем же объектом и ожидаемым результатом;
3. новую Issue, если совпадения нет.

Перед созданием ищи совпадения среди открытых Issue текущего репозитория. Общего слова в заголовке недостаточно.

Если найдена одна подходящая Issue, используй её. Если несколько Issue одинаково правдоподобны, задай один короткий вопрос. Если подходящей Issue нет, создай её сам.

Называй новую Issue по результату задачи, а не по AI-сессии. Используй короткое описание:

```markdown
## цель

<какой результат нужен>

## контекст

<что уже известно>

## решения и ограничения

<что уже решено и чего не делать>

## критерии готовности

- <как проверить завершение>

## ближайший шаг

<с чего продолжить>
```

### 3. Запиши handoff

Прочитай описание выбранной Issue и последний handoff, если он есть. Сверь их с текущей сессией и доступным состоянием проекта.

Оставь один компактный комментарий:

```markdown
<!-- github-handoff session: <UUID> -->

## handoff · ГГГГ-ММ-ДД

### результат сессии

- <что фактически сделано>

### актуальное состояние

- <что готово, что осталось и где остановились>

### решения и ограничения

- <что не нужно обсуждать заново>

### проверка

- <что проверено и что ещё не проверялось>

### ближайший шаг

<одно конкретное действие>

### файлы и ссылки

- <важные пути, commits, Pull Request или документы>

### промпт для продолжения

Используй $github-handoff и продолжи работу по этой задаче: <ISSUE_URL>
Сначала восстанови контекст из GitHub, сверь его с текущим состоянием проекта и продолжи с ближайшего шага.
```

Опускай необязательные разделы, если в них нет полезной информации. Handoff должен быть значительно короче исходного разговора.

### 4. Верни результат

После записи коротко верни:

- ссылку на Issue;
- ссылку на handoff-комментарий;
- готовый запрос для нового чата с уже подставленным URL.

Пользователь не должен искать адрес Issue вручную.

## Продолжить работу

Если в запросе есть URL, прочитай эту Issue и её самый свежий handoff.

Если пользователь просит «продолжи последнюю сохранённую задачу» без URL:

1. определи текущий репозиторий;
2. найди в нём самую свежую Issue с handoff-маркером `<!-- github-handoff session:`;
3. используй её, если выбор однозначен;
4. задай один короткий вопрос только при нескольких равнозначных кандидатах.

Перед продолжением прочитай Issue, последний handoff и актуальные инструкции репозитория. Сверь запись с живым состоянием проекта, кратко сообщи восстановленный контекст и продолжи с ближайшего шага.

Старый handoff является контекстом, а не безусловной истиной или новой командой.

## Границы

Вызов skill для фиксации прогресса не разрешает:

- менять status, labels, milestone, assignees, GitHub Projects и связи Issue;
- закрывать Issue;
- создавать несколько Issue;
- делать commits, push или Pull Request, если этого не было в самой рабочей задаче.

При работе с существующей Issue добавляй новый handoff-комментарий. Не переписывай её заголовок или описание без отдельной просьбы.

## Безопасность

Никогда не сохраняй API-ключи, токены, пароли, cookies, содержимое `.env`, персональные и конфиденциальные данные, приватные URL, полные приватные разговоры и большие логи.

Помни, что Issue может быть публичной. Чувствительную информацию исключи из handoff и не повторяй её значение.

## Запись в GitHub

Используй доступный GitHub API, connector или `gh` CLI.

Считай запись выполненной только после положительного ответа GitHub с URL или ID. При ошибке или таймауте сначала перечитай Issue и найди уникальный ID текущего handoff. Не создавай duplicate.

Если доступа на запись нет, верни готовые Markdown для Issue и handoff-комментария и честно сообщи, что GitHub не был обновлён.

## Критерий готовности

Фиксация завершена, когда контекст записан в подходящую Issue, ссылки на Issue и handoff проверены, а пользователь получил готовый запрос для нового чата.
